# Midnight raid encounter picker (2026-10-14)

## Cause and supported API path

The user reported that targeting each of Venomous Abyss's eight living bosses in LFR did not open Spekifier. Their `/spek debug` showed an active raid, actual difficulty 17, enabled parent/LFR preferences, no combat, and `restricted-target-identity`. The previous resolver required a readable target GUID before Journal name discovery or NPC fallback. A complete NPC map could not overcome that prerequisite.

Blizzard's current generated [Unit API documentation](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitDocumentation.lua) marks `UnitGUID` and `UnitName` with identity secrecy predicates. The [predicate definitions](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/SecretPredicatesDocumentation.lua) cover enemy unit identities; outside-combat state does not guarantee readable boss identity. [C_Secrets](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/SecretPredicateAPIDocumentation.lua) can report whether identity is secret, but does not provide an alternate readable identity. Sources inspected 2026-10-14; the user's output establishes the immediate live failure, not live acceptance of this replacement.

The replacement uses `GetInstanceInfo()` for game instance and actual difficulty, `C_EncounterJournal.GetInstanceForGameMap()` for Journal instance, then `EJ_GetEncounterInfoByIndex(index, journalInstanceID)` for localized encounter choices. Blizzard's [Journal API](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/EncounterJournalDocumentation.lua) documents the game-map lookup, and its [Journal UI](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_EncounterJournal/Mainline/Blizzard_EncounterJournal.lua) demonstrates encounter enumeration. The resolver retains the existing explicit-instance argument; the inspected Journal UI enumerates its selected instance, so the explicit-instance contract remains a live-validation obligation rather than something established by that UI example. Discovery does not select/change the shared Journal, query unit identity, or depend on a static raid catalog. Loot queries retain the existing query/restore transaction and use the selected Journal encounter plus actual difficulty.

Enumeration is bounded at 100 entries; empty, malformed, duplicate-ID or unterminated lists remain unavailable with diagnostics. Entry retries are bounded at five one-second attempts and reevaluate the current instance/combat/dismissal state. No bypass of secret values is attempted.

## Behavior and automated evidence

Raid entry selects the first Journal encounter by default and opens subject to existing parent/difficulty settings. The player chooses the upcoming boss using `Encounter:` beside Shared loot; the default does not infer the next boss or current LFR wing. Selection is session/visit state, survives target changes, combat and difficulty changes, resets on exit/different raid, and falls back to the first current entry if the selected encounter disappears. Changing encounter changes comparison only. Loot spec still changes only after a player clicks a specialization and the game confirms it.

The picker uses the existing native dropdown template. Its 340-pixel area and 12-pixel gap are reserved from shared-icon scrolling; both labels share the same vertical alignment. The raid row stays present during loading/empty/error states. The header shows raid/difficulty; dungeon previews hide the picker and reclaim its horizontal space. Stale menu callbacks revalidate live instance/context and combat; old loot and selection callbacks cannot repopulate a new context. Target event subscriptions and obsolete NPC mappings are retired.

Dismissal survives retargeting. Raid automatic opening is once per visit, on entry. Combat, boss kills/wipes, encounter/difficulty changes and settings toggles never rearm a displayed prompt. A never-shown initial entry prompt may still be delivered after combat. Manual reopening retains the selected encounter without advancing it; dungeon reminders remain once per visit. Manual opening works when automation is disabled. Encounter selection is not saved across reloads and does not guarantee that a player changes loot spec before a pull.

Validation: native Lua 5.1 with LuaFileSystem, `lua spec/run_tests.lua`: all eleven suites, syntax and exact manifest validation pass. Current suites include 293 lifecycle/resolver/debug checks, 48 provider/window checks, 378 preference checks and 527 skin/layout checks. Luacheck 1.2.0 reports zero warnings/errors across 30 runtime files. Mocks cover all eight Abyss encounters at all four modern raid difficulties, uncatalogued raids, forbidden target API reads, delayed catalogs, fresh/stale menu callbacks, encounter/difficulty request invalidation, both skins, 2/3/4 specs, three screen sizes, minimum layouts and absence of shared loot. Native widget appearance, hit testing, explicit-instance enumeration and client API timing require live acceptance. The native Lua packaging launcher produced `dist/Spekifier-encounter-picker-candidate.zip`; independent ZIP verification passed integrity, exact 33-file `src/` set and byte equality (57,056 bytes).

## Miniboss reopening correction (2026-10-14)

Historical implementation evidence below is superseded by the entry-only clarification at the end of this document. Current live acceptance uses the entry-only candidate.

The user reported repeat popups after defeating level-92 minibosses. The cause was resetting raid dismissal on every `PLAYER_REGEN_ENABLED`, combined with continuous eligibility of a resolved raid picker. This was a combat lifecycle bug, independent of mob level or identity.

A raid visit now records whether its prompt was displayed, including manual display and successful loot-spec selection. Only paired Blizzard `ENCOUNTER_START`/`ENCOUNTER_END` events in the same visit and actual difficulty rearm it after that. Runtime event encounter IDs are paired with one another and are never compared with Journal encounter IDs. Encounter start closes/blocks the preview even if lockdown state has not yet updated. Encounter end may rearm while still in combat; display waits for combat to clear. Unpaired, duplicate, wrong-ID, wrong-difficulty, old-visit and dungeon encounter events cannot rearm a raid prompt. Both kills and wipes qualify; selected encounter and preferences remain unchanged. This does not identify mobs by level or read secret unit identities.

API evidence: Blizzard's [encounter event definitions](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/EncounterInfoDocumentation.lua), inspected 2026-10-14, expose encounter ID and difficulty on start/end, with success on end and no secret-payload annotation on these events. Initial unshown entry remains eligible after combat, while an already-shown reminder stays consumed through ordinary combat, duplicate entry/zone events, retries, reinitialization, preference toggles and difficulty changes.

Automated validation: all eleven native Lua 5.1 suites, syntax and manifest checks pass, including 434 lifecycle/resolver/debug checks. New coverage exercises repeated level-92/non-encounter combat at all four raid difficulties with shown, dismissed, selected and manually opened previews; actual boss kills/wipes and event ordering; duplicate/unmatched events; visit/difficulty changes; disabled preferences; dungeon independence; deferred entry and manual reopening. The new candidate is `dist/Spekifier-raid-prompt-fix-candidate.zip`. Live verification remains pending in PLAN.md; no in-game pass is claimed.

## Raid entry only clarification (2026-10-14)

The user explicitly clarified that automatic opening is allowed once when zoning into a raid, never at the end of a boss fight. The previous real-boss reminder behavior was an incorrect assumption and is removed. Raid prompt consumption lasts for the entire visit; there is no encounter-event subscription, pairing state, active-encounter diagnostic or boss-event rearming. Manual reopening, selected encounter, combat closing and deferred initial entry remain available. Leaving/reentering grants one new prompt. Reload/login retains the existing fresh-session entry evaluation.

Validation: all eleven native Lua 5.1 suites, syntax/manifest checks pass, including 445 lifecycle/resolver/debug checks. Tests cover repeated trash/miniboss combat, boss kills/wipes, all four modern difficulties, shown/dismissed/confirmed/manual previews, preserved selection on manual reopening, re-entry, duplicate entry events, deferred initial entry, changed difficulty and settings. New live candidate: `dist/Spekifier-raid-entry-only-candidate.zip`; live acceptance remains pending.
