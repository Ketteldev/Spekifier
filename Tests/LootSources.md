# Phase 4 loot provider contract and evidence

Inspected on 2026-10-08 against Blizzard exported UI snapshot `09b9db7948abc9b9648dedaab51eb0cf3ee67b31`.

## Source selection

- [Difficulty constants](https://github.com/Gethe/wow-ui-source/blob/09b9db7948abc9b9648dedaab51eb0cf3ee67b31/Interface/AddOns/Blizzard_FrameXMLUtil/Mainline/DifficultyUtil_Base.lua) identify difficulty 8 as `DungeonChallenge`, displayed as Mythic+, and 23 separately as ordinary Mythic.
- [Blizzard Encounter Journal implementation](https://github.com/Gethe/wow-ui-source/blob/09b9db7948abc9b9648dedaab51eb0cf3ee67b31/Interface/AddOns/Blizzard_EncounterJournal/Mainline/Blizzard_EncounterJournal.lua) includes DungeonChallenge among its dropdown candidates, then tests each candidate with `EJ_IsValidInstanceDifficulty`. Inclusion in that list does not establish availability for any particular dungeon. `EncounterJournal_DisplayInstance` selects the instance without an encounter for the full instance list. `EncounterJournal_DisplayEncounter` selects a particular encounter. The loot UI enumerates `EJ_GetNumLoot()` with `C_EncounterJournal.GetLootInfoByIndex`, applies the class/spec filter through `EJ_SetLootFilter`, and ignores items flagged for another display season. Slot discovery temporarily resets and restores the slot filter. Search uses separate `EJ_GetSearchResult` APIs rather than filtering the loot enumeration.
- [Encounter Journal API documentation](https://github.com/Gethe/wow-ui-source/blob/09b9db7948abc9b9648dedaab51eb0cf3ee67b31/Interface/AddOns/Blizzard_APIDocumentationGenerated/EncounterJournalDocumentation.lua) defines the loot-info structure, slot-filter APIs, and the exact historical event spelling `EJ_LOOT_DATA_RECIEVED`, including its optional item ID and synchronous delivery.
- [Item API documentation](https://github.com/Gethe/wow-ui-source/blob/09b9db7948abc9b9648dedaab51eb0cf3ee67b31/Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua) defines `C_Item.GetItemInfo`, `RequestLoadItemDataByID`, `ITEM_DATA_LOAD_RESULT`, and `GET_ITEM_INFO_RECEIVED`.

Raid queries select the resolved Journal instance, actual raid difficulty, encounter, and class/spec. Dungeon queries select the resolved Journal instance with **Mythic difficulty 23 and no encounter**, regardless of actual entry difficulty 23 or 8. This obtains the combined boss tables without mutating any visible Guide frame or manually navigating bosses. The dungeon-to-Mythic+ pool mapping follows the user's explicit clarification that the end-of-run pool is the combined boss pool; the API evidence establishes retrieval mechanics, while live reward/item equivalence remains an acceptance check.

Dungeon entries are deduplicated by item ID and exclude `displayAsPerPlayerLoot`, which Blizzard renders as a separate bonus-loot category (e.g. recipes). Raid bonus-loot handling remains unchanged. No weekly-reward or Great Vault source is used. Query difficulty must be accepted and retained exactly; unsupported Mythic data still fails closed. `journalDifficultyID = 23` in results records the data query separately from actual entry difficulty and `lootMode = "mythic-plus"`.

The Journal link is retained for identity and future tooltips. With no known key level, dungeon results expose `rewardItemLevelKnown = false` and never supply an exact `itemLevel`. Future renderers must label the pool as Mythic+ end-of-run loot and must not describe a Journal tooltip's base level as a promised chest reward level.

## Interface and ownership

`Spekifier.LootProvider:Request(context, classID, { specID, ... }, callback, isCurrent)` returns a cancellation token. `callback(result)` receives the context snapshot, class ID, token, aggregate state, and a `specs[specID]` map. Each specialization contains a state and `items` with item IDs, original links, names, icons, slot/armor/quality metadata when available, and failure reasons where applicable. States are `loading`, `ready`, `empty`, `unsupported`, and `failed`. Ready aggregate comparisons may contain an empty specialization; aggregate empty means all specializations are empty.

Only one comparison request is active. Replacement and `Cancel(token)` prevent old timers/events from delivering. Optional `isCurrent(context)` additionally rejects invalid contexts and visits. The window owns a binding keyed by target/visit context, actual difficulty, Journal identity, player class, spec IDs, and display season. It cancels on close, combat, unsupported context, exit, or replacement. The resulting data is attached to `mainWindow.encounterData`; list rendering and selection remain Phases 5 and 6.

The 64-entry memory cache stores only completed ready/empty specialization results. Keys include kind, game/Journal instance, encounter/challenge map, actual difficulty, loot mode, reward-source kind/ID, display season, class, and spec. Pools may be reused across targets/visits; delivery always receives the new context snapshot and current visit guard. `Invalidate()` clears the cache, and challenge-map updates clear and refresh current requests. Returned data is copied so consumers cannot modify the cached pool.

## Shared Journal state and delayed data

Transactions run synchronously and serially outside combat. An open Adventure Guide is left untouched; closing it resumes blocked data retrieval. The provider never loads or opens the Guide, changes its UI fields, navigates its tabs, or changes its search. It snapshots class/spec, slot, and difficulty, and restores them even after query exceptions. Hidden Journal instance/encounter selection is recovered from existing Blizzard UI identity or observed selection calls. There is no supported public getter for the selected instance, or an established unset-selection API. If there was no observable initial selection, that internal selection cannot be restored; no visible Guide navigation is changed. This limit is explicit rather than using a fabricated getter or unverified selection ID.

Zero-count outdated tables and missing rows, links, names, or icons remain loading rather than reporting empty. Fully populated nonempty lists can become ready even while the Journal refresh flag remains set; that flag alone does not establish missing loot. Debug output reports missing-field counts for incomplete results. Queries use six attempts, one second apart, coalescing completion-event bursts. Known item identities request item data explicitly. Item completion hydrates names/icons directly without repeating a full table query, including after timeout. A late Journal completion can restart one additional bounded round for missing rows/links. Guide closure and combat end resume timed-out requests that were blocked for those reasons. Canceled requests never resume. API exceptions, unavailable APIs/difficulties, restore failures, and timeouts have distinct reasons. Self-generated synchronous Journal events cannot overlap a transaction.

## Murder Row correction

Murder Row (Journal instance 1304) reports requested difficulty 8, base difficulty 8, and available difficulties 1, 2, and 23. The user clarified that the dungeon-wide Mythic+ pool should use the combined Mythic boss tables. Accordingly, the provider now queries the full instance at difficulty 23 for all dungeon contexts, including before a key starts and while the actual instance difficulty is 8.

The Murder Row regression fixture reproduces availability of 1, 2, and 23 and now verifies ready data containing multiple bosses, deduplication, Journal restoration, and retained Mythic+ context. Debug output identifies query difficulty 23 and all-boss scope, making the in-game comparison reproducible. No external addon dataset is bundled. Unsupported-difficulty diagnostics remain useful for instances that genuinely cannot supply a Mythic table.

This implements the agreed source mapping. The live acceptance check remains open until per-spec item identities/counts are compared with the Guide and actual end-of-run rewards; mocked checks do not establish server loot equivalence.

## Paladin reference and hidden-window diagnostics

An independent calculation against KeystoneLoot's published dungeon membership and class/spec eligibility data at snapshot `9ed8f3a575988e512c39c39ee22b07afe0be9476` gives **8 equipment items each** for Holy (65), Protection (66), and Retribution (70) in Murder Row. The calculation excludes the reference's non-equipment Other slot (14). Sources: [dungeon membership](https://github.com/Wolkenschutz/KeystoneLoot/blob/9ed8f3a575988e512c39c39ee22b07afe0be9476/data/dungeons.lua) and [item eligibility](https://github.com/Wolkenschutz/KeystoneLoot/blob/9ed8f3a575988e512c39c39ee22b07afe0be9476/data/items.lua). This is an external reference check, not bundled source/data or proof of live client completion. Initial loading counts are provisional even if they happen to equal that reference.

Counts previously read only `mainWindow.encounterData`, which is cleared when the preview closes. `/spek debug` now prefers current visible-window results and can own a diagnostic request for a dismissed preview in a valid context. Diagnostic retrieval does not reopen the preview, reset dismissal, or consume another dungeon prompt. Polls coalesce an active request, and canceled partial requests restart rather than remaining loading forever. Diagnostic delivery is guarded by full current-context binding, class/spec, season, visit/difficulty, and combat. Context loss reports an explicit unavailable reason and rejects obsolete results. A missing visible-window reference is rebuilt from its active request rather than silently reporting unavailable.

Regression checks cover three repeated debug polls while data is delayed, completion with the preview hidden, closing during loading, cache reuse, preserved dismissal/visit state, combat, exit, obsolete diagnostic timers, re-entry, and repaired display references. These reproduce paths that could explain the live symptom; the user's exact close/context transition remains unconfirmed until the close/lookup diagnostics are captured.
